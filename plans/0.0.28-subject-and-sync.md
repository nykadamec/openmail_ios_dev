# Plán: subject fallback + pull-to-refresh sync (0.0.28)

**Stav:** čeká na schválení
**Návratový bod:** `Latest-Dev` HEAD `284059d` (0.0.27)
**Cílová verze:** 0.0.28 (MARKETING_VERSION 0.0.28, CURRENT_PROJECT_VERSION 27)

## Cíl

1. **Odesílání bez subjectu:** pokud uživatel nechá subject prázdný, odeslání musí proběhnout. Subject se uloží jako fallback `(bez předmětu)`.
2. **Pull-to-refresh reálně stáhne nové emaily:** při gestu dolů se kromě `GET /api/emails` zavolá i `POST /api/sync`, aby server natáhl nové zprávy z Resend API. Sync běží asynchronně, neblokuje UI.

## Problémy v současném kódu

- **Backend `src/openmail/routes/emails.py:90`**: `if not to or not subject: return ... 400 "Missing recipient or subject"`. Subject je tedy povinný i když ho SMTP ani Resend nevyžadují.
- **iOS `ios/openMail/Views/InboxView.swift:184`**: `.refreshable { await reload() }` volá `reload()` → `fetch(reset: true, isRefresh: true)`. `fetch` jen zavolá `GET /api/emails`, **nikdy ne `/api/sync`**. Server proto nemá šanci stáhnout nové zprávy z Resend.
- **Backend `POST /api/sync`** existuje (`routes/emails.py:100`, `resend_service.py:245`), ale **iOS ho nikdy nevolá** — `APIClient` nemá metodu `syncEmails()`.

## Navrhované změny

### A. Backend — subject fallback

`src/openmail/routes/emails.py`, `send_email_route()`:

```python
to = data.get("to", "").strip()
raw_subject = data.get("subject", "").strip()
subject = raw_subject or "(bez předmětu)"   # ← fallback
body = data.get("body", "")
if not to:
    return jsonify({"error": "Missing recipient"}), 400
result = resend_service.send_email(to, subject, body, data.get("attachments", []))
```

- žádná jiná změna logiky odesílání,
- fallback je stejný pro všechny klienty (i web),
- `resend_service.send_email` ukládá `subject` do DB, fallback se tedy uloží i do sent složky.

### B. iOS — `APIClient.syncEmails()`

`ios/openMail/API/APIClient.swift` (přidat k existujícím endpointům):

```swift
/// POST /api/sync – spustí synchronizaci s Resend API. Vrací počet importovaných.
func syncEmails() async throws -> SyncResult {
    var request = URLRequest(url: url("api/sync"))
    request.httpMethod = "POST"
    let (data, response) = try await perform(request)
    try validate(response)
    return try decode(SyncResult.self, from: data)
}
```

`SyncResult` (nový model) – dekóduje `{"imported": N}`.

### C. iOS — `InboxView.reload()`

`ios/openMail/Views/InboxView.swift`, `reload()`:

```swift
private func reload() async {
    lastVisibleEmailID = nil
    shouldRestoreScroll = false
    searchTask?.cancel()
    await loadMeta()
    // Spustit sync na pozadí, nečekat na výsledek.
    Task.detached(priority: .utility) { [weak token] in
        guard let token else { return }
        _ = try? await token.client.syncEmails()
    }
    await fetch(reset: true, isRefresh: true)
}
```

- `token` je potřeba zachytit mimo closure, protože `authStore.sessionToken()` vrací nový objekt každým voláním (podle stávající konvence v kódu).
- `Task.detached(priority: .utility)` zajistí, že sync běží mimo hlavní aktualizační task, neblokuje refresh feedback, nekončí s chybou pokud selže (Resend rate-limit, timeout).
- i nadále `fetch` provede klasické `GET /api/emails` — po úspěšném sync budou nové emaily v odpovědi.

### D. iOS — chybové hlášení

Pokud sync selže v detached tasku, v tichosti se ignoruje (try?). Pull-to-refresh stále ukáže výsledek `fetch`. Bez alertu.

Pokud by `fetch` selhal, zobrazí se stávající `refreshFailureMessageKey` (oranžový banner). Chování beze změny.

## Rizika

- `token` capture v `Task.detached` může držet reference na session po odhlášení — `try?` na selhání tiché, žádný memory leak (token je malý struct/class).
- Dvě souběžné `GET /api/emails` (pokud by uživatel refreshoval rychle za sebou) — `requestGeneration` v `InboxView.fetch` už řeší, stará odpověď se ignoruje.
- Backend sync může trvat 5–30 s, ale neběží v UI vlákně, takže neblokuje.
